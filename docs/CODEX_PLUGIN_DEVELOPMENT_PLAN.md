# План развития AGTY AI Assistant до полноценного интерфейса Codex в IDEA

Дата согласования: 17 ноября 2026 года.

Статус: реализация P0–P5 подготовлена в 0.14.0; P6 проходит итоговую приёмку. Наличие ZIP само по себе не является подтверждением всех платформ и пользовательских сценариев.

### Выполнено 17 ноября 2026 года

- P0: документация и инструкции согласованы, зафиксирован stable/experimental контракт CLI 0.169.0, воспроизводимая генерация схем и каталог покрытия. Исходные незакоммиченные изменения сохранены.
- P1: долгоживущие соединения сервиса проекта, RPC по ID, независимые подписки, фоновые чаты, очередь записи по реальному cwd, адресная остановка и восстановление наблюдения без повторного `turn/start`. Смена модели не создаёт скрытый fork.
- P2: компактная панель, доступность команд по контексту, клавиатурный выбор, офлайн-вкладка справки с поиском, aliases, связанными статьями, примерами и рабочей последовательностью. Markdown генерируется из тех же ресурсов.
- P3: единый поток/история, постраничная загрузка, полные результаты и изображения отдельно от preview, обновление DOM с сохранением выделения. Команды/файлы/права/вопросы и MCP form/URL проходят явное подтверждение; решения ограничены серверным списком, включая постоянные amendments.
- P4: снимки фактической пользовательской базы, Local History, операции create/modify/delete/rename, построчный diff, Diff Viewer, отдельные task/Git views и проверяемый откат файла/hunk/задачи. Неподтверждённые shell-изменения показываются без автоматического отката.
- P5: 55 обработчиков и 63 статьи канонического каталога; восемь терминальных/отложенных функций явно обозначены по согласованным границам. Native review/compact/goal, Plan, steer/очередь, авторизация, интеграции, агенты и worktree. `/stop`/`/clean` останавливают фоновые терминалы; `/interrupt` — turn.
- P6: локальные `test buildPlugin verifyPluginStructure verifyPlugin` проходят; реальный CLI проверен в отдельном временном проекте, нативный JCEF проверен отдельно. CI расширен проверками и артефактами на трёх ОС. Итоговые измерения, платформы и ограничения фиксируются в [P4_P6_VALIDATION.md](P4_P6_VALIDATION.md).
- Исторические результаты предыдущих этапов: [P0_VALIDATION.md](P0_VALIDATION.md), [P1_P3_VALIDATION.md](P1_P3_VALIDATION.md).

Цель — сделать плагин основным интерфейсом для работы с Codex: постановка задач, управление сессиями, команды, подтверждения, наблюдение за инструментами и просмотр изменений кода внутри IDEA. Отдельное требование — встроенная страница справки с объяснениями и примерами каждой команды.

## 1. Согласованные решения и границы

- Целевая платформа первого полного релиза: IntelliJ IDEA **2025.3**, ветка платформы **253**, Linux, Windows и macOS.
- Сохранить Java 21, Gradle Wrapper и существующую основу Swing/JCEF. Переписывание на другой стек не требуется.
- Использовать установленный **Codex CLI**. Добавить обнаружение бинарника, проверку совместимости и вход через интерфейс плагина. Автоматическая установка и обновление CLI не входят в согласованный объём.
- Эталон протокола первого полного релиза — **Codex CLI 0.169.0**, установленный и исследованный при аудите. Стабильные и необходимые экспериментальные возможности учитывать раздельно.
- Codex самостоятельно изменяет файлы в рамках разрешений; плагин показывает изменения и предоставляет безопасный откат. Предварительное принятие каждого diff не является основным сценарием.
- Для новых пользователей — **Auto: sandbox проекта и интерактивные подтверждения**. Существующие настройки доступа сохранить при миграции. Полный доступ включается отдельным явным действием.
- Переключение чатов и скрытие панели не останавливают задачи. В списке чатов видны выполнение и ожидание ответа пользователя.
- Основные сценарии и команды реализовать внутри UI плагина, без резервного перехода в терминал IDEA. Внешний браузер для OAuth остаётся частью штатной авторизации.
- Полностью покрыть рабочие сценарии разработки: команды, сессии, планы, инструменты, изменения, MCP, skills, apps, плагины Codex, агенты и worktree.
- Голос, pets, удалённые серверы и терминальные особенности оформления — последующий этап.
- Ollama как отдельный провайдер плагина, собственное автодополнение и дополнительные функции старого ТЗ не входят в этот план. Общую расширяемость провайдеров сохранить.

Этот документ задаёт актуальные приоритеты Codex-интеграции. Противоречия со старым ТЗ и описанием пустого проекта в AGENTS.md устранить на P0.

## 3. Интерфейс для узкого окна

Ориентир — ширина **320–480 логических пикселей**, без горизонтального скролла всей панели. Горизонтальная прокрутка допустима внутри отдельного блока кода или подробного diff.

```text
[Название чата ▾]                  [+] [⋯]

Лента сообщений и действий

▾ Main.java                     +12 −4
  41 − прежняя строка
  41 + новая строка
       Открыть сравнение

[Контекст: 2 файла ▾]
┌────────────────────────────────────┐
│ Сообщение…                         │
└────────────────────────────────────┘
[+] [Команды ▾]                   [↑/■]
[Модель · high · Auto ▾]
```

- Верхняя строка: выбор чата, новый чат, дополнительное меню. Название сокращать по доступной ширине; UID показывать в подробностях и подсказке.
- Панель ввода: добавление контекста, список команд и одна позиция для отправки/остановки. Во время выполнения текст можно подготовить; отправка предлагает «Уточнить текущую задачу» или «После завершения».
- Параметры запроса: один компактный элемент открывает модель, effort, режим Plan/работы и разрешения. Режим планирования и права на изменение файлов остаются раздельными настройками.
- Контекст: сворачиваемый список файлов, выделений, диагностик, diff и изображений. Просмотр, удаление и отключение находятся внутри списка.
- Редкие действия: настройки, экспорт, диагностика, архивирование и управление интеграциями находятся в меню и списке команд. Постоянные `Status`, `Review`, `Undo` убрать.
- Изменения: открытие diff и откат разместить рядом с конкретным файлом или итогом задачи.
- Подтверждения: заметная карточка в соответствующем чате; для фонового чата — индикатор ожидания ответа и уведомление IDEA.
- Справка: открывается из меню, через `/help` и из выбранного пункта списка команд. Отдельная постоянная кнопка не требуется.

Список команд открывается кнопкой и вводом `/`. Он поддерживает поиск по имени и русскому описанию, категории, подсказки аргументов, клавиши ↑/↓, Enter и Esc. Недоступная команда показывает причину. Неизвестная команда сохраняет введённый текст и не отправляется модели. Сохранить `//` для буквального текста, начинающегося с `/`.

## 4. Архитектура и обработка Codex

### Транспорт и выполнение

Сохранить `codex app-server` как основной механизм интеграции. Зафиксировать схемы эталонной версии и матрицу совместимости в проекте. Не считать новый номер версии CLI автоматическим подтверждением совместимости; доступность функций определять по проверенному контракту, настройкам и возможностям сервера/аккаунта.

Создать сервис проекта, управляющий долгоживущим процессом, соединением и задачами всех чатов. Панель подписывается на состояние и не владеет выполнением. Закрытие проекта корректно прерывает принадлежащие плагину задачи и завершает его процесс; процессы сторонних клиентов не затрагиваются.

Вместо общей очереди ответов использовать сопоставление RPC по ID. Разделить ответы, уведомления и запросы сервера. Обрыв соединения запускает сверку состояния исходного turn. Автоматическая повторная отправка пользовательской задачи запрещена: восстановление наблюдения не должно создавать повторный `turn/start`.

Разрешить несколько активных чатов. Для одного рабочего каталога выполнять не более одного изменяющего turn одновременно; независимые worktree могут работать параллельно. Ожидающую задачу показывать в очереди.

### Контракты

Заменить набор перегрузок `newRequest(...)` структурированными параметрами запроса. Ввести:

- `RequestOptions` — модель, effort, режим, разрешения, каталог и вложения.
- `ThreadState` и `TurnState` — выполнение, очередь, ожидание пользователя и результат.
- Типизированные события сообщений, команд, изменений, планов, инструментов и предупреждений.
- `PendingServerRequest` — запрос подтверждения или ввода, допустимые ответы и состояние разрешения.
- `CommandDescriptor` — команда, aliases, аргументы, доступность, обработчик и ссылка на справку.
- `CommandHelp` — назначение команды, сценарии, примеры, ожидаемые результаты и ограничения.
- `ChangeSet` — операции над файлами, исходное и итоговое состояние, hunks и связь с turn/item.

Сохранить общий контракт провайдера. Поддержку другого AI-провайдера не делать условием завершения Codex-интеграции.

### Ответы и история

Единый обработчик состояния обслуживает прямой поток и восстановление истории. События обновляют существующие элементы по `threadId/turnId/itemId`; финальный снимок заменяет накопленные данные без дублирования.

| События | Представление |
| --- | --- |
| Сообщения, публичные пояснения, планы | Потоковый текст, отдельные пункты плана и их состояния |
| Выполнение команд | Команда, cwd, поток вывода, длительность, exit code, результат |
| Изменения файлов | Тип операции, путь, `+N/−N`, построчное сравнение |
| MCP, apps, динамические инструменты | Инструмент, аргументы, прогресс, результат, ошибка и вложения |
| Агенты и подагенты | Родительская задача, состояние, переход в соответствующий чат |
| Поиск и изображения | Запрос, результаты, ссылки, локальные изображения и артефакты |
| Compaction, review, ожидание, hooks | Отдельные понятные состояния выполнения |
| Лимиты, ошибки, предупреждения | Статус с подробностями и доступными действиями |

Обрабатывать `turn/diff/updated`, `item/fileChange/patchUpdated`, потоковый вывод команд и обновления плана. Неизвестные пользовательски значимые события показывать универсальной карточкой; служебные сохранять в диагностике. Внутренние рассуждения не выводить, использовать публичные пояснения.

Историю загружать постранично. Состояние интерфейса и черновики хранить отдельно от нативной истории Codex; старые локальные сообщения мигрировать без потери данных. Большие результаты раскрывать и загружать по запросу. Ограничение объёма видимой карточки не должно уничтожать данные, необходимые для полного просмотра и diff.

Обновлять изменённые карточки вместо пересоздания всей HTML-ленты. Сохранить поведение автопрокрутки, копирования, безопасных ссылок и Swing fallback.

### Diff и откат

- Разбирать структурированные операции создания, изменения, удаления и переименования файлов.
- В чате показывать unified diff с номерами строк, знаками `+`/`−` и цветами темы IDEA. Подробное сравнение открывать в штатном Diff Viewer.
- Разделить «Изменения этой задачи» и «Все изменения рабочего дерева». Второе представление включает staged, unstaged и untracked.
- Уже выполненные Codex изменения повторно не применять. Старый ручной импорт patch оставить отдельным действием.
- Перед изменяющей задачей сохранять документы рабочего каталога и ставить метку Local History. Для затронутых файлов сохранять доступные версии и хеши.
- Откатывать выбранный файл, hunk или задачу только после проверки текущего состояния. При последующих пользовательских правках открывать сравнение/слияние. При отсутствии достоверной базы запрещать автоматический откат с объяснением.
- Создание, удаление и переименование учитывать как операции, а не как запись пустого или нового текста в прежний путь.
- Обновлять VFS по мере изменений, включая завершение с ошибкой и отмену. Не добавлять автоматическое форматирование поверх правок Codex.
- Откат истории диалога и откат файлов должны быть отдельными действиями. Не использовать `git reset --hard` для отмены изменений агента.

### Разрешения и вопросы

Реализовать подтверждения команд, файловых операций, дополнительных прав, вопросы модели и MCP elicitation. Показывать только допустимые сервером решения, связывать ответ с конкретным запросом и предотвращать повторный ответ. Учитывать `serverRequest/resolved`, отмену и закрытие задачи. Истечение времени само по себе не предоставляет разрешение.

Режимы доступа: чтение, Auto и полный доступ. Ограничения администратора и реальные возможности sandbox имеют приоритет. Правила исключения контекста плагина не представлять как изоляцию самого Codex. Неподдерживаемая платформа или настройка sandbox не должна молча переводить задачу в полный доступ.

## 5. Команды и интеграции

Использовать единый реестр для списка, подсказок и справки. Slash-команды являются действиями клиента: их нельзя просто переслать в App Server как текст. Служебные команды выполняются через локальные обработчики/RPC; операции, требующие модели, такие как генерация инструкций или ревью, явно запускают соответствующий запрос.

| Группа | Обязательное покрытие |
| --- | --- |
| Диалоги | `/new`, `/clear`, `/resume`, `/rename`, `/fork`, `/archive`, `/delete`, `/side`, `/btw`, `/copy`, `/export` |
| Задачи | `/plan`, `/goal`, `/review`, `/compact`, `/recap`, уточнения активного turn и очередь сообщений |
| Модель и доступ | `/model`, `/permissions`, `/approve`; доступные аккаунту параметры скорости и специальные режимы |
| Проект | `/mention`, `/ide`, `/init`, `/diff`, `/cd`, `/pwd`, `/cwd`, `/worktree`, `/presets` |
| Интеграции | `/skills`, `/mcp`, `/apps`, `/plugins`, `/hooks`, `/memories`, `/import` |
| Наблюдение | `/status`, `/usage`, `/warnings`, `/debug-config`, `/agents`, `/subagents`, `/ps`, `/stop` |
| Настройки | `/config`, `/experimental`, `/logout`, `/feedback`, `/help`; настройки оформления и клавиш через IDEA |

Для `/stop` восстановить значение CLI 0.169.0: остановка фоновых терминалов; `/clean` — alias. Текущий turn останавливают кнопка `■` и отдельная команда плагина `/interrupt`. Изменение семантики отметить в миграции и справке.

Выбор модели действует на следующий turn без скрытого создания ответвления; fork выполняется явно. `/review` запускает ревью Codex, а просмотр изменений выполняется через `/diff`.

Интеграции управляются через Codex: список и включение skills, MCP OAuth и состояния серверов, apps, установка/удаление плагинов, hooks и их доверие. Авторизация использует существующее хранилище Codex; ключи не записываются в историю и XML настроек плагина. Изменение глобальной конфигурации должно быть отдельным явным действием; параметры обычного запроса не переписывают её.

Worktree создавать через Git с выбором ветки и каталога, затем привязывать к отдельному чату. Смену cwd разрешать только для неработающей задачи с обновлением контекста и области разрешений.

На P0 классифицировать каждую команду эталонного CLI: нативный эквивалент в плагине, действие через UI IDEA, условная доступность по аккаунту/версии или явно отложенная функция. Скрытые отладочные команды не включать в обычный пользовательский список. Незавершённую реализацию не обозначать как недоступность со стороны Codex.

## 6. Страница справки с примерами каждой команды

### Размещение и навигация

Добавить встроенную страницу **«Команды Codex — руководство и примеры»**. Она открывается отдельной вкладкой в редакторной области IDEA, чтобы подробные примеры не занимали узкое окно чата. Повторное открытие активирует существующую вкладку. Справка поставляется с плагином и работает без сети, авторизации и подключения к модели.

Точки входа:

- `/help` открывает каталог команд.
- `/help <команда>` открывает описание конкретной команды; принимать имя с `/` и без него.
- Меню плагина содержит «Справочник команд».
- Выбранная команда в списке имеет действие «Описание и примеры».

Страница содержит поиск по командам, aliases, русским описаниям и сценариям, категории, якорные ссылки и возврат к списку. Текущую доступность команды показывать с учётом CLI, аккаунта, ОС и состояния задачи. Описание недоступной команды остаётся доступным.

### Содержание каждой команды

Для каждой пользовательской команды эталонного каталога, включая aliases, дополнения плагина и явно отложенные команды, указать:

1. Назначение простыми словами и ситуации, когда команду стоит применять.
2. Синтаксис, обязательные/необязательные аргументы, значения по умолчанию и aliases.
3. Как вызвать команду текстом и где находится её эквивалент в UI.
4. Не менее двух практических примеров: быстрый сценарий и сценарий с аргументами либо другим контекстом использования, если аргументов нет.
5. Ожидаемый результат: что появится в интерфейсе, изменится ли контекст, начнётся ли запрос к модели, затрагиваются ли файлы или настройки.
6. Требования и ограничения: версия, ОС, авторизация, права, доступность во время выполнения.
7. Типичные ошибки, способы исправления и связанные команды.
8. Отличия от CLI, если действие адаптировано к IDEA, и статус реализации в плагине.

Aliases ведут к основной статье и не требуют дублирования объяснений. Для модели, UID и путей использовать явно обозначенные подставляемые значения; не выдавать вымышленные идентификаторы за работающие.

Обязательно подробно объяснить пары `/review` и `/diff`, `/new` и `/clear`, `/resume` и `/fork`, `/compact` и `/recap`, `/stop` и `/interrupt`, а также различие Plan и режима доступа. Отдельно показать рабочую последовательность: выбрать модель → добавить контекст → получить план → выполнить задачу → просмотреть изменения → запросить ревью.

Примеры имеют действия **«Копировать»** и **«Вставить в чат»**. Вставка не выполняет команду автоматически и не уничтожает существующий черновик. Для многошагового примера пользователь выбирает отдельный шаг. Действия, меняющие файлы, удаляющие сессии или настройки, сопровождаются точным описанием эффекта.

### Источник данных и сопровождение

Метаданные команд и справку связать через стабильный ID `CommandDescriptor`/`CommandHelp`. Синтаксис, aliases и условия доступности брать из общего реестра; тексты и примеры хранить в ресурсах плагина. Не поддерживать отдельные несогласованные списки команд для UI и документации.

Предусмотреть воспроизводимую генерацию читаемой Markdown-версии в `docs/CODEX_COMMANDS.md` из того же источника. Этот файл создаётся при реализации справочника; в рамках сохранения плана его содержимое не считается уже подготовленным.

На P2 реализовать страницу и её работу на уже поддержанных командах. На P5 довести содержание до полного согласованного каталога. Для каждой новой команды готовность включает обработчик, справочную статью, примеры и проверки.

## 8. Проверки и критерии приёмки

- **Протокол:** перемежающиеся ответы RPC, несколько чатов, повторные события, неизвестные поля, разрыв соединения, отсутствие повторного `turn/start`, большие результаты.
- **Подтверждения:** разрешение, отказ, отмена, ответы на вопросы, несколько ожидающих запросов, переключение чата и разрешение запроса другим клиентом.
- **Изменения:** создание, удаление, переименование, несколько файлов, Unicode, CRLF, отсутствие финального перевода строки, большие и бинарные файлы, отмена посередине работы.
- **Сохранность:** пользовательские изменения до и во время задачи, несохранённые документы, конфликтующий откат, частичная ошибка применения, миграция старой истории.
- **Интерфейс:** ширины 320/360/480 px, масштаб 100–200%, светлая/тёмная тема, клавиатура, длинные пути, стабильная прокрутка, JCEF и Swing fallback.
- **Справочник:** статья и примеры для каждой команды, рабочие ссылки и aliases, `/help <команда>`, поиск, офлайн-доступ, корректная недоступность по версии/ОС, сохранение черновика, отсутствие исполнения при копировании/вставке. Проверять примеры по реестру аргументов без запуска действий с побочными эффектами.
- **Сквозной сценарий:** войти → открыть CLI-сессию → выбрать команду → получить план → ответить на вопрос → подтвердить операцию → наблюдать правки и тесты → открыть diff → безопасно откатить выбранную правку.
- **Фоновые задачи:** переключиться между чатами без отмены; увидеть ожидающее подтверждение; остановить только выбранную задачу; корректно сериализовать изменяющие задачи одного рабочего каталога.
- **Выпуск:** `test`, `buildPlugin`, `verifyPluginStructure` и Plugin Verifier для IDEA 253; CI на Linux, Windows и macOS. Интеграционные тесты используют фиктивный App Server; проверка с реальным Codex проводится в отдельном тестовом проекте.

Для экспериментальных возможностей фиксировать конкретные версии и условия доступности. Не обещать совместимость с непроверенными версиями IDEA или CLI.

## 9. С чего начать в новой сессии

Начать с **P0**, затем переходить к **P1**. UI, diff и расширение списка команд опираются на корректные события, состояния задач и двусторонний протокол.

Первые действия разработчика:

1. Прочитать этот план и актуальные инструкции репозитория. Проверить рабочее дерево и сохранить существующие незакоммиченные изменения.
2. Сверить исходную версию плагина и установленный CLI. Зафиксировать схемы и матрицу покрытия для 0.169.0, включая справку и экспериментальные методы.
3. Восстановить загрузку зависимостей JetBrains и запустить текущие тесты, сборку ZIP и проверку структуры. Зафиксировать реальные результаты, отдельно от старых отчётов.
4. Уточнить README/AGENTS.md и старое ТЗ по фактической структуре и текущим приоритетам. Исправить CI для рабочей ветки и запланированной матрицы ОС.
5. На P1 выделить сервис проекта и маршрутизацию RPC. Первый сквозной результат: задача продолжает работать при переключении чата, события приходят в правильную сессию, остановка адресована только выбранному turn.

Текст для запуска новой сессии:

> Прочитай docs/CODEX_PLUGIN_DEVELOPMENT_PLAN.md и инструкции репозитория. Начни реализацию с P0, затем переходи к P1. Сохрани существующие изменения рабочего дерева. Веди проверки по критериям плана и отмечай выполненные этапы в документе. Встроенный справочник с примерами каждой команды входит в обязательный объём P2/P5.
